Project scopes now use explicit types: `{ "kind": "all" }`, `{ "kind": "unassigned" }`, or `{ "kind": "project", "name": "exact project name" }`. Genuine names such as `all`, `__none__`, or JSON-looking text remain literal project names. A saved named project that is currently absent stays empty instead of widening to all tasks.

New saved-view exports use JSON 1.1 and strictly validate these scope objects. Imports accept 1.0 and 1.1; legacy stored strings and 1.0 files keep their former meanings (`all` for all projects, `__none__` for no project). Unrelated operations do not rewrite old saved-view configurations. Older app versions that only accept view-file 1.0 must be updated before reading 1.1 exports. Task JSON remains 2.4 and IndexedDB remains version 2.

This is not a blanket backward-configuration guarantee: the actual 4.6 archive treats a non-string project filter as `all`. An old window can therefore display a new typed view as All projects and write that interpretation back. Close or refresh every older tab and installed-app window before editing new saved views. Before downgrading, retain a separate views 1.1 export, then return to 4.7 or newer to import it; old apps cannot read that file. Existing task-field upgrade/rollback evidence does not establish typed-view compatibility with old interfaces.

## Product wording

A storage-failure draft is retained only in the current page's memory. The banner downloads all queued forms as a separate `type: task-draft`, version 1.0 JSON reference file, not a restorable task backup; task Import does not accept it. Retry reconnects storage without reloading while drafts remain, and resumed edits still preserve the original task snapshot for stale-write checks. Discard is explicit and per draft. Refreshing, closing or crashing the page can lose the queue. These files can include unsaved text and the original edited task, so review them before sharing.

Starting a browser download does not prove that the user saved or retained a usable file. Backup coverage can describe the task snapshot offered for export, not durable storage outside the browser. Task JSON, CSV, saved-view files and diagnostic reports retain their separate purposes; no cloud backup or draft-autosave service is added.

A dirty-form prompt can reduce accidental loss, but browser departure dialogs are controlled by the browser and may be limited, especially on mobile. Unsaved text remains vulnerable to crashes or storage/profile loss. A first offline installation still requires a completed online app-shell cache. Older active workers use their own previously installed caching policy; a new worker cannot retroactively change that policy. The real 4.6 archive-to-candidate path with failed language resources and worker update has a focused Chromium result below. The candidate HTML includes a non-executable JSON translation fallback matching its own resource version. If an external language request fails, startup uses that language from the same HTML rather than an older translation bundle. Its generation and static consistency checks and the focused browser upgrade cases passed. The reproducible candidate package and complete integrated run passed as recorded below.

## Translation maintenance

After changing external translation files, configured languages or the language resource version, regenerate the embedded data and then refresh CSP hashes:

```bash
python3 tools/translation_fallback.py --write
python3 tools/security_policy.py --write
python3 tools/check.py --static-only
```

Static validation compares the embedded resource version and full language content with the external JSON files. The fallback is data, not executable script; the application is still served as static files without a runtime build step. Deploy HTML, worker and language resources together.
