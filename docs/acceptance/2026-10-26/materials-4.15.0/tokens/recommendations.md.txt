# 4.14.0 material-token source review

Read-only analysis of `index.html` SHA-256 `e5741f889cb3c8e74d7f5885f36d5030922afa948b397579b759839ffd827f48`. This is CSS/cascade analysis, not a screenshot audit. No repository files changed. Operate/craft-floor and current DESIGN.md informed the recommendations; the unavailable Impeccable launcher was not retried.

## Material roles

Keep the existing eight theme palettes and geometry. Add independent `--material-*` roles derived from existing semantic colors:

- **Field:** light `color-mix(in srgb,var(--bg-surface-raised) 65%,var(--bg-surface-alt))`; dark `color-mix(in srgb,var(--page-bg) 85%,var(--bg-surface-alt))`. Inputs currently share `--bg-surface-alt` with their containing properties panel, so only the control border separates them. These proposals give fields their own plane without changing content or accent colors.
- **Sheet:** current content surface with one restrained contact shadow. Avoid giving task rows their own shadows or radii. Apply to `.workspace-task-surface`, `.settings-surface`, `.stats-review` and main calendar/timeline container where appropriate.
- **Inset:** preserve the darker tool/property plane, using a small derived edge highlight if it is needed to read the recess. Apply to `#taskEditor .task-editor-properties`, `.workspace-overview`, `.tools-drawer`, `.stats-action-grid`; preserve the fact that statistics uses distinct review/project planes.
- **Raised:** opaque `--bg-surface-raised` with stronger, offset float shadows. Group `.task-action-menu`, `.dropdown-menu-content`, `.custom-select-menu`, `.command-palette-panel`, `.batch-more-panel`; dialogs use a separate, larger shadow. Avoid tinting readable overlay bodies transparent.
- **Chrome:** optional translucent sticky top bar/mobile dock only, where moving content exists behind it. Use a dedicated material-chrome role plus existing solid fallback. Do not add blur to static cards or fields.
- **Controls:** keep primary action stronger than secondary controls. A small inset top highlight/contact shadow is enough; no new card-hover motion or per-row lift. Preserve danger and selected states.

Separate light/dark highlight/shadow strengths. Dark mode needs a restrained lighter edge as well as shadow; black shadow alone cannot define nearby dark surfaces. Shadow colors can derive from the active theme's text/sidebar roles rather than the older universal blue shadow pigment. Keep card radii at 12–16px and circular dismiss/more controls; a new all-component roundness is unnecessary.

## Contrast calculations

`source-contrast.json` records exact source values for all eight variants. Across existing page/content/inset/raised colors, source minimums are main text **8.13:1**, secondary **5.25:1**, tertiary **5.02:1**. Primary on-color minimum is **6.72:1**. The proposed field mixes retain secondary/placeholder minimum **6.06:1** and control-border minimum **3.47:1**. Values are direct sRGB token calculations, excluding opacity, compositing, hover, native controls and actual rendered axe checks. Preserve current text colors rather than lowering opacity to make layers feel soft.

## Cascade and safety traps

1. Theme variable rules at lines 1276–1283 have attribute specificity. A final bare `:root {--field-bg:...}` or `--chrome-bg` does not beat them. Independent `--material-*` tokens applied by final component selectors avoid copying eight palettes or fighting specificity.
2. Native `select.search-input` carries its chevron via `background-image`. Set only `background-color` for common field styling; `background:` clears the arrow. Native date/time controls must keep `color-scheme` and affordances.
3. `#taskEditor #taskName` intentionally has a transparent face, bottom divider and distinct focus outline. Exclude it from generic recessed fields. The final form/editor rules at 1685 onward override earlier `.form-panel-*` material styling.
4. Search uses later `#searchInput`/`.search-input` declarations; task form has higher-specificity rules. Inspect computed styles, not only the first selector match.
5. Existing `.btn-primary/.btn-secondary:disabled`, semantic danger selectors, pressed states, and focus-visible rules must remain effective. Avoid a generic `.btn {box-shadow:...}` winning later over disabled cleanup, or a material background winning over danger/selected backgrounds. Keep focus as a distinct visible outline, not only a soft shadow.
6. Existing no-backdrop and reduced-transparency fallbacks occur before the final theme block. New chrome/overlay rules after them need their fallback media/support rules repeated after the new styles, or opaque fallback will lose to the new material rule.
7. Global reduced-motion rule already forces animation and transition durations to `.01ms !important`; do not introduce new decorative or load animation. Avoid changing overflow, positioning or z-index while refining shadows: the batch menu and mobile editor/footer have protected geometry.
8. Current source has no explicit forced-colors block. Do not force palette colors over the browser. Scope new decorative effects away from forced-colors, or turn gradients/shadows off there and use system-color boundaries for floating surfaces, preserving checked/selected/focus states. This requires rendered checking before any high-contrast claim.

Recommended acceptance: all eight theme/mode variants for the same real task/editor content, dark/light menus, 320/390/desktop widths, focus/disabled/selected/error states, no-backdrop/reduced-transparency fallback and forced-colors/reduced-motion. Screenshots judge hierarchy; geometry and existing targeted checks protect behavior.
